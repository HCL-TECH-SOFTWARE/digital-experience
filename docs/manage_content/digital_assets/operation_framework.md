# Operations framework 

One integral part of HCL DX Digital Asset Management is the so-called "operations framework". This tooling allows DAM to run asynchronous background processes.
 
The operations framework consists of four key components:

- For storing `operations` we leverage our `DAM database`. On top of it sits a **`scheduler`** which always looks for `operations` that need to be handled and will assign those to **`workers`**. Those **`workers`** receive the `operation` to be handled from the scheduler and will return their results after being done.

---
## Glossary

### Operation
A specific task that needs to be performed. Will be stored in the DAM database and handled by the scheduler.
### Worker
A forked task will be created by the DAM main process. This `worker` will receive the `operation` from the DAM main process and carry out the work necessary. After the work is done, it will report back to the master. It can only handle one `operation` at a time. A worker has a metadata value called `lastTouched` which is used to determine how long a `worker` is in its current state. 
### StatusUpdate
Will be sent by the `workers` to the DAM scheduler to inform about the result of handling an `operation`.  
### Scheduler
The `scheduler` is the controlling mechanism of the framework of the operations. It takes care of creating `workers`, feeding them with `operations` to work on and, ensuring expired `operations` and expired `workers` are being cleaned up.
### Scheduler heartbeat
The `scheduler heartbeat` defines the intervals in which the `scheduler` will try to claim `operations` for `workers`. This can be configured.  
## List of operations 

In the following sections, we described some of the operations that normally run in DAM. 

## Rendering & Media Processing Operations

| Operation | Description |
|------------------|-------------|
| **prepareRenditions** | Analyzes uploaded media file and creates metadata structure determining which renditions need to be generated based on media type configuration (image, video, document, etc.). Examines file characteristics, dimensions, codec information, and file size to determine optimal rendition targets for web display, mobile viewing, and previews. Creates rendition specifications for resolution, format, quality level, and compression settings. Executed immediately after file upload validation. Returns array of RenditionObject with target specifications. Related to: generateRendition, generateThumbnail. Input: Media item with file type, size, and storage location. Output: Queued rendition generation operations. |
| **generateRendition** | Generates image/video renditions in multiple formats and sizes (web-optimized 1920x1080, 1024x768, 640x480, 320x240, etc.) from source media file. Uses Image Processor API for images (applies compression, color space conversion, EXIF stripping) and video codec libraries for videos (transcodes to H.264, VP9, or other formats with varying bitrates). Creates preview versions suitable for different devices and network conditions. Standard priority (40) for derivative renditions; Original rendition priority (20) for source files to ensure fast availability. Stores generated file with media storage entry and metadata. Reports success/failure status. Retry up to 3 times on failure before marking as FAILED. Related to: prepareRenditions (precursor), generateThumbnail. Input: Rendition specification object with target dimensions, format, quality, target storage path. Output: Generated file stored in media storage with linked metadata record. |
| **generateThumbnail** | Creates small preview thumbnail images (typically 200x200px, configurable size) from source media file or first rendition for display in UI galleries, collection browsing, and search results. Extracts first key frame from videos, crops best region from images, generates placeholder for documents. Standard priority (40) executes after main renditions. **Original thumbnail priority (10) - HIGHEST priority in entire system** - ensures original file preview instantly available to users without waiting for derivative renditions. Thumbnail embedded in media_item record for quick access. Input: Rendition object or media storage with thumbnail dimension specifications. Output: Thumbnail image file (typically JPEG or PNG) stored in media storage and linked to media_item and/or rendition record. Database: Stores thumbnail_url in media_item and rendition records for direct access. |
| **generateSupplement** | Generates supplementary or auxiliary renditions beyond primary renditions, primarily used for video processing workflows. Creates proxy files for faster timeline scrubbing in video editors, low-resolution preview versions for streaming over poor connections, HD/4K versions for archive, or alternative format versions (e.g., AVIF, WebP) for browser compatibility testing. Can also generate sprite sheets for efficient thumbnail delivery. Related to video transcoding pipeline. Input: Video rendition specifications with supplementary format requirements, target resolution, codec, bitrate. Output: Supplementary rendition file stored in media storage with metadata entry. |
| **generateKeyword** | Extracts and generates keyword metadata from media file content using natural language processing, OCR (images), text analysis (documents), or speech-to-text (videos). Identifies topics, subjects, entities, places, and searchable terms from file content to enable enhanced full-text search and discoverability. Works across file types: Images (OCR text extraction + visual analysis), Documents (text content parsing), Videos (transcript analysis if subtitles available). Keywords stored in media_item.metadata as array of string values. Input: Media storage object with file path and file type indicator. Output: Keyword array stored in media_item metadata field for full-text search indexing. Related to: generateMetaData. |

## Metadata Operations

| Operation | Description |
|------------------|-------------|
| **generateMetaData** | Extracts comprehensive technical and descriptive metadata from uploaded file via Image Processor API integration. Collects: Image metadata (width, height, DPI, color space, color profile, EXIF camera info, ISO sensitivity, white balance, lens info, GPS coordinates if available). Video metadata (duration in seconds, codec, frame rate, bitrate, resolution, audio track count, bitrate per track, subtitles). Document metadata (page count, author, creation date, modification date, file encoding). Executes POST request to `IMAGE_PROCESSOR_API_FULL_URL/images/getMetaData` with file stream. Response includes all extracted properties. Metadata state tracked (PENDING→SUCCESS or PENDING→FAILED). Retry on failure up to 3 times. Priority 50 (lower priority than renditions as metadata not blocking display). Input: Media storage ID with file location, file type, storage path. Output: Metadata object stored in media_storage.metadata and optionally in media_item.metadata. Related to: generateKeyword, Track media state. Timeout: 1800000ms (30 min). |
| **updateMetaData** | Updates media item record with extracted metadata from generateMetaData operation. Takes metadata object from Image Processor API and persists into media_item and media_storage database records. Updates metadata state field from PENDING to SUCCESS. Creates event log entry for audit trail marking metadata update action. If metadata extraction state is SUCCESS, preserves existing state in metadata object. Falls back to operation.inputs.state if available. Input: Media item ID, media storage ID, complete metadata object from extraction. Output: Updated media_item and media_storage records with new metadata. Database changes logged in event_log table. Related to: generateMetaData (precursor). |
| **validateThumbnail** | Quality assurance operation that validates generated thumbnail images for proper resolution, file size, format compliance, and visual quality. Checks thumbnail exists, is accessible, meets minimum quality standards. Verifies thumbnail displays correctly without corruption. Can trigger re-generation if validation fails. Used to ensure all thumbnails meet UI performance requirements. Input: Thumbnail file path and validation criteria (dimensions, file size limits, format). Output: Validation result - either PASSED (thumbnail marked as valid) or FAILED (thumbnail queued for regeneration). Related to: generateThumbnail, retrigger operations. |

## Cleanup & Maintenance Operations

| Operation | Description |
|------------------|-------------|
| **cleanupMedia** | Removes temporary and orphan files related to media items after deletion or processing completion. Cleans up: Temporary upload chunks, extract intermediate files from processing, failed rendition partial files, cache files, working directories from processors. Frees disk space by removing unnecessary files that remain after media operation failures or completion. Executed periodically and after deleteMedia operations. Does not delete original media file (handled by deleteStorage). Input: Media item ID or list of media IDs to cleanup. Output: Removed temporary files from storage, freed disk space. Related to: deleteMedia (parent operation), cleanupCollections. Database: No database changes; filesystem only. |
| **cleanupCollections** | Removes empty collection references and cleanup collection metadata after deletion or move operations. Deletes: Unused collection_media_relation entries, orphaned collection records marked for deletion, stale access_reference_id entries. Consolidates parent-child relationships for moved items. Performed post-deletion as housekeeping. Input: Collection ID or list of collection IDs for cleanup. Output: Cleaned collection records, optimized collection hierarchy. Related to: deleteCollection, cleanupMedia. Database: Modifies collection table, collection_media_relation table. |
| **deleteOrphanDirectoryAndMedia** | Recursively removes directories and media items from filesystem that have no corresponding database references. Identifies lost files/folders with orphaned storage entries or completely missing database records. Critical for recovering from failed migrations, incomplete imports, or corrupted database states. Safety mechanism - verifies no active database references before deletion. Traverses storage directory tree comparing filesystem entries against media_storage table. Input: Storage root path to scan. Output: Deleted orphan files and directories, cleaned filesystem state. Related to: deleteOrphanMediaStorage. Safety: Logs all deleted items for audit trail. |
| **deleteOrphanMediaStorage** | Removes media storage entries whose parent media items no longer exist in database. Typically occurs after incomplete uploads, failed import operations, or database cleanup. Identifies media_storage records pointing to non-existent media_item records. Deletes storage entry and associated files from filesystem. Prevents database referential integrity violations. Frequently triggered after deleteMedia operations to ensure consistency. Input: Media storage object or media storage ID. Output: Deleted media_storage entry, removed physical files from disk. Related to: deleteMedia, deleteOrphanDirectoryAndMedia. Database: Removes from media_storage table. |
| **clearTrash** | Permanently deletes soft-deleted items (media, collections, versions) after configured retention period expires. Soft-delete lifecycle: Item marked deleted with timestamp → Remains in database for retention period (default 30 days) → After retention expires, marked for permanent deletion → clearTrash operation finds and permanently removes. Configured via environment: TRASH_CLEARANCE_TIME_IN_DAYS (default 30), TRASH_CLEARANCE_HEARTBEAT_IN_MINUTES (default 60 - how often to check). Feature flag: ENABLE_TRASH_AUTO_CLEARANCE (default: true). Cascades complete deletion of all child records and files. Input: None (scans all trash automatically). Output: Permanently removed items and associated files, freed database and filesystem space. Related to: deleteMedia, deleteCollection, soft-delete operations. Scheduled operation: Runs on configurable intervals. |

## Delete Operations

| Operation | Description |
|------------------|-------------|
| **deleteMedia** | Soft-deletes media item with cascading cleanup of all related data structures (renditions, versions, favorites, storage, custom URLs, collection relationships). Records deletion timestamp and deletes_by user. Does not immediately remove physical files - handled by deleteStorage operation. Creates delete event log entry for audit trail. Item remains in database for TRASH_CLEARANCE_TIME_IN_DAYS (default 30 days) enabling recovery before permanent deletion. Cascading deletes: All rendition records, all version records, all favorite entries for media, all media_storage entries, all custom_url entries, all collection_media_relation entries linking to media (removes from collections). Input: Media ID, createDeleteEvent flag (whether to create audit event). Output: Media marked as deleted with soft-delete timestamp, related records remain (can be recovered), cascade delete completion status. Related to: deleteStorage (physical file deletion), clearTrash (permanent deletion after retention), deleteIndexedDocumentsByQuery (search index cleanup). Database: Sets deleted flag and delete_date in media_item table. |
| **deleteStorage** | Physically removes uploaded file and rendition files from filesystem and storage service after media deletion confirmed. Only called after deleteMedia operation succeeds. Deletes: Original uploaded file from storage, all rendition files, all supplementary files, metadata cache files. Verifies files exist before deletion. Logs deleted file paths for audit trail. Completes the media deletion workflow by removing permanent storage footprint. Input: Storage delete specification object containing storage location paths and file IDs to delete. Output: Deleted files removed from filesystem, storage service updated. Related to: deleteMedia (logical delete precursor), fileStorage service integration. |
| **deleteCollection** | Soft-deletes collection and cascades delete to all child collections and media items within collection hierarchy. Records deletion timestamp. Item remains in database for retention period enabling recovery. Cascading deletes: All child subcollections (recursive), all media items in collection (calls deleteMedia for each), all collection_media_relation entries, all access_reference_id entries in Ring API access control system, all associated permissions and role assignments. Input: Collection ID to delete. Output: Collection marked as deleted, all child records cascade-deleted, audit event created. Related to: deleteMedia (cascaded for media), deleteStorage (cascaded for storage), clearTrash (permanent deletion after retention). Database: Sets deleted flag in collection table recursively. Ring API: Deletes resource permissions via access control service. |
| **deleteOperations** | Removes completed, failed, or expired operation records from operation table to prevent unlimited growth. Housekeeping operation that cleans stale records. Retention policy: Failed operations retained for FAILED_OPERATION_THRESHOLD_TIME_HOURS (default 24 hours), keeps up to FAILED_OPERATION_THRESHOLD_LIMIT_RECORDS (default 20000 records). Successful operations deleted immediately after completion (keeping only recent for audit). Input: Operation ID list or status criteria query (status = SUCCESS, status = FAILED with old timestamp, status = ABORTED). Output: Deleted operation records, compact operation table. Related to: OPERATION framework housekeeping. Database: Removes from operation table. Logging: Deleted operation details logged before removal. |
| **deleteIndexedDocumentsByQuery** | Removes documents from full-text search engine (Elasticsearch) after media/collection deletion to maintain search index consistency. Prevents deleted items appearing in search results. Executes query against search index matching: media_id, collection_id, or last update timestamp criteria. Deletes matching documents from search index. Can batch delete multiple items efficiently. Input: Query specification (by media ID, collection ID, timestamp range, or other criteria). Output: Removed search documents, search index synchronized with database. Related to: deleteMedia (logical deletion), deleteCollection (logical deletion). Search: Integrates with search engine API. |

## Indexing & Search Operations

| Operation | Description |
|------------------|-------------|
| **initiateInitialIndexing** | Creates initial full-text search index of all media items and collections for search engine (Elasticsearch). Executed: First deployment, after search index corruption, major schema changes, or manual reindex request. Scans entire media_item and collection tables. Builds searchable documents with: Media name, description, keywords, metadata fields. Collection name, description, hierarchy. Creates inverted index enabling full-text search across all fields. Can take minutes to hours for large repositories (100k+ items). Input: Optional scope parameter (all items, media-only, collections-only). Output: Indexed documents in search engine, search functionality enabled. Related to: initiateReIndexing (repair/refresh), processAssetsForIndexing (incremental). Performance: Heavy I/O operation - typically run during maintenance window. |
| **initiateReIndexing** | Triggers complete rebuild of search index from ground-up with cleanup of stale documents. Full index rebuild: Deletes existing search index, creates fresh index structure, re-indexes all records from database, verifies index consistency. Used for: Index corruption recovery, major search configuration changes, search quality improvements, after significant data cleanup. Heavier operation than initial indexing as it rebuilds from scratch. Input: Rebuild options (full rebuild vs. incremental, index name). Output: Fresh search index with current documents, old stale documents removed. Related to: initiateInitialIndexing (similar scope), invalidateIndexedContent (marks for re-index). Performance: Very heavy operation - run during off-peak hours, can impact search availability during execution. |
| **processAssetsForIndexing** | Batch-prepares media items for search indexing in groups (typical: 100-500 items per batch). Extracts metadata, builds searchable document structure, queues index operations. Used for: Batch indexing during off-peak hours, incremental indexing of new/updated items, parallel processing via worker pool. Input: List of media item IDs to index (can specify batch size). Output: Queued index operations for each asset, document structures built. Related to: processAssetsDocumentBuilding (precursor), initiateInitialIndexing (full index creation). Performance: Efficient batch processing. |
| **processAssetsForLiveIndexing** | Real-time indexing of media items immediately after creation/modification to keep search index current. Triggered automatically after: Media upload completion, media metadata update, media moved to different collection. Ensures users find items in search 1-2 seconds after creation. Higher priority than batch indexing. Immediate index update visible to search queries. Input: Media item object with current data and changes. Output: Updated search index document, search available immediately. Related to: processAssetsForIndexing (batch version), invalidateIndexedContent (marks stale). Performance: <1 second latency for search availability. |
| **processAssetsDocumentBuilding** | Transforms media item metadata into structured searchable document format suitable for search engine indexing. Builds document structure with: Text fields (name, description, keywords for full-text search), facet fields (media type, size range, date range for filtering), hierarchy fields (collection path for nested search). Handles type coercion (dates, numbers), field mapping (database column → search field), content enrichment (keywords, tags). Intermediate step before indexing. Input: Media item with complete metadata, media type, storage info. Output: Structured document JSON ready for indexing. Related to: processAssetsForIndexing (executes before), full-text search engine. |
| **invalidateIndexedContent** | Marks indexed content as stale/invalid requiring re-indexing. Prevents stale content appearing in search results after configuration changes, bulk updates, or quality improvements. Triggers re-indexing on next scheduler cycle. Input: Content scope (media IDs, collection IDs, timestamp range, or all). Output: Stale flag set on indexed documents, re-indexing scheduled. Related to: initiateReIndexing (executes update), processAssetsForIndexing (incremental update). |
| **processCollectionsForIndexing** | Indexes collection hierarchy and metadata enabling search within collections and collection-based filtering. Indexes: Collection metadata (name, description), hierarchy information (parent-child relationships), path information (breadcrumb for filtering), permissions (if permission-based search). Input: Collection ID list or scope (all collections, specific branch). Output: Indexed collection documents with full hierarchy. Related to: processCollectionsDocumentBuilding (precursor), initiateInitialIndexing. |
| **processCollectionsDocumentBuilding** | Builds searchable document structure from collection metadata and hierarchy. Constructs: Collection name/description fields, hierarchy path fields (enables collection path search), permission fields (for restricted search), collection statistics (item count, size). Input: Collection object with hierarchy information and metadata. Output: Structured collection document ready for indexing. Related to: processCollectionsForIndexing (executes after). |
| **processAssetForDeletion** | Removes deleted media item document from search index synchronizing index with database deletion. Prevents deleted items appearing in search results. Called after deleteMedia/deleteIndexedDocumentsByQuery. Input: Media ID or media ID list. Output: Removed search documents, index synchronized with database removal. Related to: deleteMedia (logical deletion), deleteIndexedDocumentsByQuery (alternative deletion). |

## Version Management Operations

| Operation | Description |
|------------------|-------------|
| **versionRetention** | Enforces version history limits per media item and removes excess old versions according to retention policy. Retention policy configurable: Max versions per media item (typical: 5-10, default: 3), Min retention period (keeps versions for minimum X days), Latest version always retained regardless of limits. Triggered automatically via scheduler (configurable frequency via VERSION_RETENTION_INTERVAL). Deletion: Removes oldest versions first when exceeding limits, keeps specified minimum retention period. Input: Media ID with retention policy parameters (max versions, retention days). Output: Excess old versions deleted, media_version table cleaned. Database: Removes version records, associated version files deleted via deleteStorage cascade. Related to: Media versioning system, cleanup operations. |
| **regenerateRenditionOrVersion** | Re-generates renditions or versions for existing media items enabling: Format conversion (convert JPEG rendition to WebP), Quality improvement (increase JPEG quality from 80 to 95), Recovery from failed generation, Codec/format standardization across repository, Archive creation in new format. Can apply to single media item or batch of items. Input: Media/rendition/version ID with regeneration specifications (new format, quality, resolution), optional version label. Output: New rendition/version file generated, linked to media item, old version optionally retained. Related to: generateRendition (similar operation on new uploads), manual triggering from UI for format conversion. |

## Upload & Post-Action Operations

| Operation | Description |
|------------------|-------------|
| **schedulePostActions** | Orchestrates multi-step post-upload operation workflow executing in sequence. Triggered immediately after file upload completed and uploaded file validated. Priority 30 (high - core upload workflow). Schedules: prepareRenditions → generateRendition → generateThumbnail → generateMetaData → indexing operations → Kaltura upload (if video). Creates dependency tree ensuring operations execute in proper sequence. Post-Actions queued: 1) Metadata extraction from Image Processor, 2) Rendition preparation and generation, 3) Thumbnail generation, 4) Search indexing, 5) State tracking and progress updates. Input: Media item with upload details (file ID, collection, user info, storage location). Output: Multiple operations queued in operation table with proper sequencing, media state set to PROCESSING. Related to: Upload workflow orchestration, media post-actions execution. |
| **trackMediaState** | Continuously tracks and updates media upload/processing state providing progress visibility. Updates state through lifecycle: UPLOADING (file transfer in progress), PROCESSING (renditions/metadata generation active), READY (all processing complete, available for use), FAILED (processing failed, manual intervention needed). State changes: Broadcast to UI via WebSocket or polling, stored in media_item.state field, logged to event_log for audit. Used for: Progress bars in UI, completion notifications, error reporting. Input: Media ID with current operation status update. Output: Update media_item.state field, push state change event to connected clients, log state change. Related to: All media processing operations. Real-time: Enables live progress tracking. |

| **syncStagingMismatchSearch** | Comprehensive diagnostic operation finding and reporting all staging mismatches across entire system. Used for: System health checking, identifying sync gaps, manual remediation guidance. Input: Sync scope (all or specific resource types). Output: Detailed mismatch report (can be voluminous). Related to: Sync diagnostics, system health monitoring. |

## Content Management Operations

| Operation | Description |
|------------------|-------------|
| **contentCreateUpdate** | Publishes create and update events when media items or collections created/modified. Events trigger: External system notifications via webhooks, analytics/tracking updates, integration point for connected applications (WCM, portal, etc.). Event types: MEDIA_CREATED (new media), MEDIA_UPDATED (media modified), COLLECTION_CREATED (new collection), COLLECTION_UPDATED (collection changed). Event payload includes: Resource type, resource ID, change timestamp, modified fields, user who made change. Published to: Event bus/message queue for subscribers, external webhook endpoints. Input: Content object with changes (media or collection). Output: Event log entry created, webhooks triggered, external systems notified. Related to: System integration, external notifications. Asynchronous: Fire-and-forget event publishing. |
| **contentDelete** | Publishes deletion events when media or collections deleted. Notifies external systems of item removal enabling: External system cleanup (WCM removing references, analytics updates). Event types: MEDIA_DELETED (media removed), COLLECTION_DELETED (collection removed). Event includes: Resource ID, deletion timestamp, reason for deletion. Input: Deleted content ID and type. Output: Event log entry created, delete events published, external webhook triggered. Related to: System integration, cascading cleanup. |
| **purgeEvents** | Removes old event log entries preventing unlimited event_log table growth. Retention policy: Default 90 days (configurable via EVENT_LOG_RETENTION_DAYS), keeps all recent events, deletes events older than threshold. Scheduled periodic execution (configurable interval). Batch deletion for efficiency. Input: Purge criteria (age threshold, optional resource type filter). Output: Deleted old event records, freed database space. Database: Removes from event_log table. Related to: Database maintenance, log archival. |
| **updateSyncStatus** | Updates and maintains synchronization progress status during staging sync operations. ### Failed operations clean up job

Naturally, it might happen that the list of operations in the DAM database gets quite long. The operations cleanup job ensures to clean up obsolete operations to make sure the list doesn't get cluttered. This kind of obsolete operations includes e.g. failed operations, etc. It is configurable for how long obsolete operations will be kept before they get finally cleaned up.
-   Naturally, it might happen that the list of operations in the DAM database gets quite long. The operations cleanup job ensures to clean up obsolete operations to make sure the list doesn't get cluttered. This kind of obsolete operations includes e.g. failed operations, etc. It is configurable for how long obsolete operations will be kept before they get finally cleaned up.
#### Configuration attributes in `values.yaml` 

- Maximum threshold time

`failedOperationThresholdTimeHours` determines the maximum threshold time for failed operation jobs after which failed operations will be deleted. 

```yaml
configuration:
  digitalAssetManagement:
    failedOperationThresholdTimeHours: 24
```

- Threshold limit of records

`failedOperationThresholdLimitRecords` determines the maximum threshold limit of failed operation job records. If the threshold is met, the failed operations will be deleted.

```yaml
configuration:
  digitalAssetManagement:
    failedOperationThresholdLimitRecords: 20000
```
